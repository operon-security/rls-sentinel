CRITICAL documents
Policy exposes all rows (USING true)
Policy "docs_all" on "documents" (SELECT) uses USING (true) for the public role, so any client reads every row in the table.
Replace with an ownership check, e.g. using (auth.uid() = user_id).
CRITICAL profiles
Row Level Security is disabled
Table "profiles" is reachable by the anon role(s) but RLS is OFF. Every row is readable by anyone holding the public anon API key. This table looks user-owned (user_id), so this is a cross-tenant data leak.
alter table "public"."profiles" enable row level security; -- then add per-operation policies
HIGH api_keys
Insert policy has no WITH CHECK
Policy "keys_ins" on "api_keys" (INSERT) has no WITH CHECK, so an inserted row's ownership column is not validated — a user can create rows assigned to another user.
Add with check (auth.uid() = user_id) to the policy.
HIGH subscriptions
Policy checks authentication, not ownership
Policy "subs_read" on "subscriptions" (SELECT) only requires the caller to be logged in (no auth.uid() = owner check). Any authenticated user can reach every other user's rows.
Add an ownership predicate, e.g. using (auth.uid() = user_id).
MEDIUM subscriptions
Ownership column "user_id" is nullable
On "subscriptions", "user_id" allows NULL. A row with a NULL owner matches no "auth.uid() = user_id" policy, so it is invisible and un-deletable through the API, and a service-role insert that omits the owner creates an unprotected orphan row.
alter table "public"."subscriptions" alter column "user_id" set not null; -- after backfilling any NULLs

INFO api_keys
RLS is not forced (service role bypasses it)
On "api_keys", RLS is enabled but not FORCED, so the service-role key bypasses it (by design). Any server code using that key must scope queries to a verified user id.
Resolve identity server-side with getUser()/getClaims(), never the unverified getSession(); optionally: alter table "public"."api_keys" force row level security;
